SAP Version Upgrade — Security Team's Role

1. Pre-Upgrade Assessment

  • Run SU25 impact analysis on existing roles/authorizations — the new version may change or deprecate transactions
  • Take inventory of custom roles vs SAP-delivered roles
  • Check the GRC risk ruleset — new T-codes can introduce new SoD risks

2. SU25 Steps (core of the upgrade for Security)

  • Step 1: Initial Fill of customer tables (SU24 data) — only for the first-time upgrade
  • Step 2A/2B: Preparation — compare old vs new SAP default values (USOBX/USOBT changes)
  • Step 2C: Automatically adjust roles against the new authorization defaults
  • Manually review conflicts where the customer had already modified authorization values

3. Role Impact Analysis

  • Map new/changed/deprecated transactions to existing roles
  • Reflect newly added/removed authorization objects in roles
  • Handle Fiori catalog/group changes if moving to S/4HANA (classic to Fiori shift)

4. GRC Ruleset Update

  • Update/reimport the SAP standard ruleset for the new version (to cover risks from new T-codes)
  • Re-run risk analysis on existing roles — clean up new false positives/negatives

5. Testing

  • Regenerate test roles in QA/Sandbox (PFCG mass generation)
  • UAT (User Acceptance Testing) with key users — especially for Fiori tiles/apps if it's an S/4HANA move
  • Use authorization trace (ST01/STAUTHTRACE) to catch missing authorizations

6. Cutover & Go-Live

  • Move roles to Production via controlled transport
  • Keep Emergency Access (Firefighter ID) ready for go-live support
  • Monitor post-go-live — use SU53/trace to catch real-time authorization issues
One-line answer for "SAP upgrade steps as Security" The core of a Security team's upgrade work is SU25 — reconciling old vs new authorization defaults, impact-analyzing and updating roles, refreshing the GRC ruleset against new T-codes, and running authorization trace-based testing before go-live so access doesn't break.
